静态博客的难点不在于页面能不能渲染，而在于读者能不能稳定地读完一篇长文。短页面可以依靠视觉风格撑住第一眼，但长文章最后还是要回到排版的基本功：字号、行高、段落间距、列表缩进、标题节奏，以及正文区域和导航区域之间的边界。

这次调试的目标很简单：让博客看起来更正式，减少卡片式装饰，把注意力还给内容。页面不需要用阴影证明自己是一个模块，也不需要每个块都被包进圆角容器。真正有用的是信息之间的层级关系，以及读者在滚动时能否快速判断自己读到哪里。

## 先确定阅读栏宽

阅读栏宽会直接影响每一行的阅读负担。太窄会让中文段落频繁换行，句子被切得太碎；太宽则会让眼睛在行首和行尾之间来回搜索，尤其是在桌面大屏上更明显。

这次保留了一个相对克制的正文宽度，让标题、摘要、正文和代码块都在同一个阅读轴线上展开。这样做有几个好处：

- 标题不会像落在一个独立卡片里，而是自然成为文章正文的开头。
- 段落行长保持稳定，长句不会铺得过满。
- 目录可以放在右侧，但不抢正文的视觉权重。
- 图片、图表和代码块不会把阅读节奏打断得太明显。

正文宽度不是越大越高级。对于技术文章来说，一行文字通常还会混入英文、路径、命令、参数名和版本号。如果行宽过大，读者扫描这些混合文本时会更累。

## 字号和行高

正文最终采用接近 `16px / 24px` 的节奏。这个比例并不夸张，但足够稳定。行高太小会让中文段落发灰，行高太大则会让段落显得松散，读者需要更多滚动才能获得同样的信息密度。

段落之间的外边距也需要谨慎。许多页面看起来“不正式”，不是因为字号错了，而是因为每个段落上下距离都太随意。正文里的段落、列表、引用和代码块应该像同一套排版系统里的成员，而不是各自拥有完全不同的垂直节奏。

一个可执行的判断标准是：

1. 连续三个普通段落放在一起时，不应该显得拥挤。
2. 段落后接无序列表时，列表应该像段落的自然延伸。
3. 列表后接小标题时，小标题需要足够的上边距，让读者意识到语义已经切换。
4. 代码块前后需要留出空间，但不能像插入了一张独立海报。

这些判断都很朴素，但比单纯调整颜色更重要。

## 列表应该服务扫描

无序列表在技术文章里出现得非常频繁。读者通常不会逐字阅读列表，而是先扫关键点，再决定是否回到上文。列表的排版要支持这种行为。

这次对列表做了几项细节处理：

- 缩进减少到足够清晰但不过度内收的位置。
- 每个列表项保留稳定的垂直间距，避免项目之间粘在一起。
- 嵌套列表的上下边距单独收紧，避免形成大块空白。
- `marker` 使用弱化颜色，让项目符号提示结构但不抢内容。
- 列表项中的段落保留较小间距，防止多段列表项变成松散卡片。

列表的关键不是“好看”，而是让读者可以快速复述出结构。

## 标题层级

标题的作用是给文章建立骨架。一级标题属于文章头部，二级标题负责切分主要章节，三级标题解释章节内部的局部议题。它们之间需要有足够明显的层级差，但不需要通过复杂装饰来完成。

这次去掉了正文二级标题下面的横线。横线会让每个章节都像一个新的卡片区块，尤其当页面已经有顶部边界和列表分隔线时，横线数量会快速变多。没有横线以后，标题靠字号、字重和上下间距建立层级，页面会更安静。

### 什么情况需要保留线条

线条不是不能用，而是要有明确职责。适合保留线条的位置通常包括：

- 页面导航和正文之间的边界。
- 文章列表中每一行之间的分隔。
- 表格的行列关系。
- 代码块工具栏和代码内容之间的边界。

如果线条只是在重复表达“这里是一个区域”，就应该删除。

## 代码和图表

技术博客不能完全取消容器感。代码块、表格和图表需要边界，因为读者要知道这些内容和普通段落的交互方式不同。比如代码块可以复制，图表可以横向滚动或放大查看，表格需要保持行列对齐。

这里的原则是：功能性边界可以保留，装饰性边界尽量减少。

```bash
npm run build
npm run dev -- --host 127.0.0.1 --port 18080
```

上面这样的代码块需要背景和边界，但不需要投影。投影会让它像一个浮在正文上的卡片，而不是文章中的一段技术材料。

## 最后的检查方法

排版调整完成后，不应该只看首页。至少要检查三类页面：

- 短文章：确认页面不会因为内容少而显得空。
- 长文章：确认滚动过程中标题、段落和列表节奏稳定。
- 图文混排文章：确认图片、图表、代码块不会破坏正文行宽。

一个静态博客的风格最终不是由某个单独组件决定的，而是由这些页面共同决定的。当每个页面都能用同一种排版逻辑解释，整个站点才会显得正式。
