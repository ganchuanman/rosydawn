轻量部署系统并不意味着可以忽略可观测性。相反，系统越轻，越需要清楚知道每一步发生了什么。因为轻量系统通常没有复杂平台兜底，也没有大量中间层帮助记录状态。一旦部署失败，开发者最需要的是快速判断失败发生在拉取代码、构建产物、替换目录、重载服务，还是证书续期这样的外围环节。

可观测性不是堆工具，而是让系统在关键路径上留下足够明确的证据。日志、状态文件、构建产物、退出码、通知消息，这些东西都可以很简单，但必须一致。

## 部署链路的关键阶段

一个静态博客的部署链路通常可以拆成几个阶段。不同项目会有不同命令，但阶段本身大致稳定：

1. 获取最新代码。
2. 安装或校验依赖。
3. 构建静态产物。
4. 校验输出目录。
5. 发布到目标目录。
6. 重载 Web 服务。
7. 记录部署结果。

每个阶段都应该能回答三个问题：输入是什么，输出是什么，失败时留下了什么证据。只要这三个问题回答清楚，很多部署问题就不会变成漫长的猜测。

### 拉取代码

拉取代码阶段的日志至少应该记录当前分支、远端提交、拉取前后的提交哈希。如果部署系统是定时执行，还应该记录本次为什么触发：是检测到提交变化，还是手动执行。

- 当前分支用于排查部署源是否正确。
- 提交哈希用于确认线上版本。
- 拉取结果用于区分“没有变化”和“拉取失败”。
- 触发原因用于回溯自动部署行为。

不要只记录“git pull success”。这句话对排查几乎没有帮助。

### 构建产物

构建阶段需要记录命令、耗时和产物目录。对于静态站点，还可以额外记录生成页面数量。如果构建工具本身已经输出这些信息，部署脚本只需要保留原始输出，不要过度加工。

```bash
npm run build
test -d dist
find dist -maxdepth 2 -type f | wc -l
```

构建失败时，最有价值的是原始错误上下文。把日志截断成最后一行通常会让问题更难排查。更好的方式是保留完整构建日志，并在通知里摘要最后几行。

## 状态文件

日志适合追踪过程，状态文件适合描述当前结果。一个简单的部署状态文件可以包含以下字段：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `commit` | 当前部署的提交哈希 | `8f31c2a` |
| `branch` | 部署来源分支 | `main` |
| `startedAt` | 部署开始时间 | `2026-04-12T10:00:00+08:00` |
| `finishedAt` | 部署结束时间 | `2026-04-12T10:00:18+08:00` |
| `status` | 部署结果 | `success` |
| `durationMs` | 部署耗时 | `18042` |

这个文件不需要复杂数据库支持。只要它在每次部署后原子更新，就足够支撑大部分查询场景。

## 通知内容

通知不是把日志搬到聊天窗口。好的通知应该让接收者在十秒内知道是否需要介入。对于成功部署，通知可以非常短；对于失败部署，通知需要给出失败阶段、错误摘要和日志位置。

一个失败通知可以包含：

- 项目名称和环境。
- 失败阶段，例如 `build` 或 `reload`。
- 当前提交和上一成功提交。
- 错误摘要，保留足够上下文。
- 日志文件路径或可点击链接。
- 下一步建议，例如“检查依赖安装”或“回滚到上一成功产物”。

> 通知的目标不是替代排查，而是减少进入排查前的信息收集成本。

## 日志分层

日志可以按用途分成三类。不要把所有内容都塞进同一个文件里，否则读者很快会失去上下文。

### 运行日志

运行日志记录部署脚本自己的控制流，比如开始、结束、跳过、重试。它应该稳定、短小，并尽量结构化。

### 构建日志

构建日志保存构建工具的完整输出。它可能很长，但最接近错误现场。构建日志不一定适合人每天阅读，但必须能被保留和定位。

### 服务日志

服务日志来自 Nginx 或其他 Web 服务。部署成功但访问失败时，服务日志是关键入口。部署脚本不需要解析所有服务日志，但至少应该在状态输出里提示它的位置。

## 健康检查

静态站点也需要健康检查。最简单的检查是访问首页并确认返回 `200`。如果站点有关键文章页，也可以挑选一两个固定路径做检查。

```bash
curl -I https://example.com/
curl -I https://example.com/blog/2026/04/static-blog-reading-notes
```

健康检查不要过度复杂。它只需要回答：部署完成后，最基本的访问是否可用。

## 回滚策略

没有回滚策略的自动部署只完成了一半。静态站点的回滚可以非常简单：保留上一版 `dist` 目录或上一版发布目录的软链接。当新版本发布失败时，把软链接切回上一版即可。

回滚策略需要提前验证，而不是事故发生时再写。检查项包括：

- 上一版产物是否完整。
- 切换软链接是否原子。
- Web 服务是否需要重载。
- 回滚后状态文件是否更新。
- 通知里是否明确写出“已回滚”。

轻量系统不需要复杂平台，但需要清楚的边界和证据。把这些清单落实以后，部署脚本会更像一个可靠的工程工具，而不是一段只能在顺利时工作的命令集合。
